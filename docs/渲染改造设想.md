# KSP 2D 渲染改造设想

> **文档状态：v0.1 设想稿 —— 待决策，非开工指令**
>
> 本文档汇总截至目前讨论过的全部渲染改造设想，供项目总监评估与决策。
> 所有选项均附成本、优缺点与风险，**最终取舍由项目总监拍板**。
> 文中数据除标注「实测」外，均为估算；估算前提见各章节。

## 一、文档目的

1. 记录渲染改造的**全部候选方向**，避免遗漏与重复讨论
2. 用**实测数据**替代直觉判断，标明每条方案的成本量级
3. 明确区分「已确认方向」与「待决策点」，不代替总监做决策
4. 给出可验证的**小成本前置验证**方案，降低决策风险

### 2.4 WebGL 能力实测

| 实测项 | 结果 |

### 2.6 现有架构中可利用的预留接口

项目已为渲染升级预留了相当完整的抽象，这是评估成本时最重要的正面因素：

| 预留点 | 位置 | 现状 |
|---|---|---|
| `RenderableManager` | `src/graphics/renderable.js` | 注释明示「预留特效接口」，layer 结构已含 `blendMode: 'normal' \| 'additive'`、`uvOffset`、`uvSpeed`、`scale`、`zIndex` |
| `bodyRenderableConfigs` | `src/graphics/bodyRenderables.js` | 已有 `star_glow`（Kerbol 远景档 **5 层叠加**）、`star_ball`、`planet_ring`（4 段环带 + feather）配置 |
| `programEffects.js` | `src/graphics/programEffects.js` | 已用 `createRadialGradient` 实现光晕与环带 |
| `SceneManager` | `src/sceneManager.js` | 干净的 `update(dt)` / `render(ctx)` 契约、`SCENE_CHANGED` 事件 |
| `EventBus` | `src/eventBus.js` | 模块间解耦通信已就位 |
| `GameState` | `src/gameState.js` | 单一状态入口 |
| `src/config/` | — | 2,330 行数据驱动配置 |

**重要结论：画面升级在现有架构下更接近「换实现」而非「改配置」——`star_glow` 的多层定义、`planet_ring` 的环带数据可直接被 GPU 后端消费。**

### 2.7 现状的三条硬约束

| 约束 | 说明 | 影响 |
|---|---|---|
| **贴图光照已烘焙** | 亮面方向固定，不随太阳位置变化；这正是「动态光照」需求的根因 | 要做动态光照，必须把 albedo 与光照解耦 |
| **圆片贴图无法自转** | 圆片是球体的单视角投影，仅含可见半球数据，不是经纬展开图 | 自转需重新产出 equirectangular 贴图 |
| **架构全静态** | `starSystemRegistry` 静态数组、`celestialBodies` 启动时构建、贴图由 `textureConfig` 预加载 | 运行时动态星球需架构级新增（详见 5.4） |

## 四、方案空间：引擎路线对比

### 4.1 路线 A —— 迁移 Unity

**内容**：完整重写为 Unity 项目（2D 玩法 1:1 平移 + 表现层升级）

| 工作项 | 人日 |
|---|---:|
| 绘制层重写（轨道 / SOI / 标记 / 天体） | 63 |
| UI 层重写（13,819 行） | 156 |
| 场景生命周期重搭 | 31 |
| 物理 / 逻辑 / 配置移植 | 33 |
| 音频重写 | 8 |
| 存档重写 | 18 |
| 测试 / 基准重写（`tools/` 15 个脚本，1,793 行全部作废） | 18 |
| 资产 / 字体再处理（294 MB 字体需重建 TMP 图集） | 12 |
| 集成联调（+30%） | 97 |
| **合计** | **410–620** |

**其中真正买到「更好画面」的部分：约 33–50 人日**（4 项效果在 Unity 侧的实现成本）
**搬家税：约 350–500 人日**

| 优点 | 缺点 |
|---|---|
| 视觉上限最高 | **不可逆**：需先烧 150+ 人日重写 UI 才能看到第一帧新画面 |
| 拿到完整工业化生态（Shader Graph / URP 2D Lights / Particle System / Post-processing） | 单人全职 20–30 个月，3 人 8–11 个月 |
| **美术可可视化协作**（唯一 Web 侧无法替代的能力） | 期间 Web 版必须停止迭代 |
| 跨平台构建（主机 / 移动） | 数值精度回归风险（JS double → C# float 混用） |
| 成熟 Profiler | 引擎版本升级长期维护成本 |

**工业化生态的真收益 vs 伪收益（针对本项目）**：

| 真收益 | 伪收益（对本项目不成立） |
|---|---|
| 美术协作工作流 ★★★★★ | 资产商店（2D 轨道力学用不上，天体为自制） |
| Shader Graph ★★★★☆ | Timeline / Cinemachine（2D 俯视用不上） |
| URP 2D Lights ★★★★☆ | Addressables（已有 `resourceSystem`） |
| Particle System ★★★★☆ | 编辑器调参（`src/config/` 已数据驱动） |
| Post-processing Volume ★★★★☆ | 内置物理引擎（使用开普勒解析解 + RK4，PhysX 用不上） |
| 跨平台构建 ★★★☆☆ | |

**触发条件**：**当项目决定引入美术/策划进行可视化协作时，Unity 才是必要选择。** 这是唯一的决策分水岭。

### 4.2 路线 B —— 新增 WebGL 特效层（推荐）

**内容**：在现有 Canvas 2D 管线之上叠一层 WebGL canvas，新增 `src/fx/` 模块，**现有代码几乎不动**。

```
gameLoop
 ├→ sceneManager.update(dt)
 ├→ sceneManager.render(ctx)      ← 现有 Canvas 2D：轨道线 / 标记 / UI（不动）
 └→ fxLayer.render(dt)            ← 新增 WebGL 层：光晕 / 粒子 / 光照 / 后处理
```

| 优点 | 缺点 |
|---|---|
| **40–60 人日**（Unity 的 1/8 ~ 1/15） | 需手写 GLSL，无可视化 Shader 编辑器 |
| **侵入点 3–8 行**，可 feature flag 随时关闭 | 美术无法在浏览器内调材质 |
| 现有逻辑 / UI / 存档 / 音频 / 配置全部不动 | 依赖 WebGL2（老旧设备需降级） |
| **可回退**：删一个目录即可 | 无跨平台主机构建能力 |
| 分 4 阶段，每阶段都有可见产出 | |
| 与星球系统**共用 WebGL 基础设施** | |

### 4.3 路线 C —— 渲染后端整体替换为 WebGL2

**内容**：把 `render(ctx)` 契约抽象为绘制原语接口，实现完整 WebGL 后端，Canvas 2D 层退役。

| 优点 | 缺点 |
|---|---|
| 完整拿到着色器能力（程序化纹理 / 大气折射 / 动态光照） | **80–110 人日** |
| 保留全部逻辑层（约 21,000 行不动） | 需重构场景渲染契约 |
| 是路线 B 的自然延续，不浪费 | 轨道线 / 标记等「数据密集但视觉简单」的部分失去 Canvas 2D 的便利 |

**建议**：**作为路线 B 之后的按需演进，不单独立项。** 当 B 的能力边界被触及（如需对轨道线本身做后处理）时再推进。

### 4.4 三路线对比

| | 路线 A（Unity） | 路线 B（fx 层） | 路线 C（整体 WebGL） |
|---|---:|---:|---:|
| 人日 | 410–620 | **40–60** | 80–110 |
| 现有代码改动 | 全部重写 | **3–8 行** | 渲染层重构 |
| 4 项画面诉求 | ✅ | ✅ 90% | ✅ 100% |
| 美术协作 | ✅ | ❌ | ❌ |
| 跨平台发行 | ✅ | ❌ | ❌ |
| 可回退 | ❌ | ✅ | ✅ |
| 精度回归风险 | 高 | 无 | 无 |

**核心判断：4 项画面效果在 Unity 侧的实现成本（33–50 人日）与 Web 侧（40–60 人日）几乎相同。Unity 路径多出的 350–500 人日，没有一分钱花在画面上。**

### 5.3 程序化星球重制

**目标**：保留 17 个星球各自风格，重建为可自转、可动态光照的高质量球面星球。

**技术路线（三层）**：

```
17 张现有贴图
    ↓ ① 风格提取（离线，一次性）
planetStyles.json   ← 色板 + 噪声频率特征 + 亮度统计 + 类型分类
    ↓ ② 程序化生成（运行时，GPU render-to-texture）
equirectangular 贴图（1024×512，经度方向无缝）
    ↓ ③ 球面渲染（运行时着色器）
带自转 + 动态光照 + 大气散射的星球
```

> **重要说明**：「用现有贴图当素材」**不是「把贴图拼接起来」**。
> 现有圆片仅有半个球面数据，拼不出可自转的球。
> 正确做法是**风格迁移**：现有资产提供「该长什么样」的审美约束（色板 + 纹理统计），像素由程序化噪声重新生成。

**层 1：风格提取（离线工具）**

| 产出 | 方法 |
|---|---|
| 主色板 5–8 色 | k-means 聚类 |
| 类型分类 | 岩质 / 冰质 / 气态 / 海洋 / 熔岩 / 荒漠 |
| 噪声频率特征 | 多尺度能量分布（决定地表粗糙度） |
| 亮度 / 饱和度分布 | 直方图统计 |

工具：`tools/gen/extractPlanetStyles.mjs`（Node，复用现有 `tools/` 脚本风格）

**层 2：星球生成器**

| 技术 | 说明 |
|---|---|
| **周期噪声** | fBm + domain warp，**经度方向必须周期化**，否则自转时接缝暴露 |
| 类型模板 | 岩质（陨石坑 + 山脊）/ 气态（条带 + 涡旋）/ 冰质（裂纹）/ 海洋（大陆 + 云）等 |
| 调色 | 从层 1 色板采样，保证风格一致 |
| 极点处理 | equirect 极区挤压补偿 |
| 输出 | GPU render-to-texture，1024×512 约 3–8 ms |

**层 3：球面渲染（自转 + 光照的关键）**

**不需要 3D 模型** —— 全屏 quad + 光线求交，球面法线是解析的：

```glsl
vec2 p = (uv - 0.5) * 2.0;
if (dot(p, p) > 1.0) discard;                 // 圆外丢弃
vec3 n = vec3(p, sqrt(1.0 - dot(p, p)));      // 球面法线（解析，无需法线贴图）
float lon = atan(n.x, n.z) + spin;            // 自转
vec2 tuv = vec2(lon / TAU + 0.5, asin(n.y) / PI + 0.5);
vec3 albedo = texture(planetTex, tuv).rgb;    // 采样经纬图
float diff = max(0.0, dot(n, sunDir));        // 动态光照
```

**同一段着色器同时拿到**：自转、昼夜面、晨昏线、边缘逆光、大气散射。

|---|---|---:|
| **原型** | 1 个星球（建议 Mun：表面最简单、最易判断成色）跑通全链路 + 与原图对比 | **8–12** |
| 主体 | 工具 + 生成器 + 渲染器 + 17 个星球对齐 | 32–48 |

### 5.4 后期扩展：无限星球（**本期不做**）

**需求**：用现有贴图风格生成无限新星球，服务探索玩法，需要自转。

**核心难点（架构级）**：

| 环节 | 现状 | 需改为 |
|---|---|---|
| 星系注册 | `starSystemRegistry` 静态数组 | 运行时动态 |
| 天体列表 | `celestialBodies` 启动时静态构建，**父先子后** | 运行时 push（注意顺序约束） |
| 贴图 | `textureConfig` 预加载 | 运行时 GPU 生成 |
| 存档 | 只存飞船 / 设施，不存天体表 | **必须存种子** |
| 扫描 | `scannedBodies[bodyId]` 按 id 索引 | 按生成 id 索引 |

**唯一设计红线：存档必须存种子，且生成算法必须版本化并冻结。** 否则玩家读档后探索过的星球会变样。

**额外成本**（在星球重制基础上）：

| 项 | 人日 |
|---|---:|
| 动态天体注册 + 物理参数生成（radius / gm / soiRadius / 轨道） | 8–12 |
| 星系生成器 + 星图 UI 扩展 | 20–30 |
| 种子存档 + 缓存（内存 / IndexedDB） | 5–8 |
| 探索玩法接口 | 依赖玩法设计 |
| **合计** | **33–50+** |

> **为什么建议后期做**：该方向**缺少验收标准**（生成结果无参照物，无法判断该不该继续投入）。
> 而「17 星球重制」有 17 张现成原图作为基准，**达标与否一眼可辨**。

