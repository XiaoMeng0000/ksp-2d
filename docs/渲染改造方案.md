## 四、星球重制路线

### 4.1 为什么是「完全程序化」

设想稿 §5.3 原方案是「从现有贴图做风格迁移」。经实测（§8），**原图不含可解耦的烘焙光照**，
曾评估过「反演可见半球 + 补全背面」路线（可保真、可量化验收），但总监决策为**完全程序化重造**，
理由是：彻底摆脱背面补全与接缝风险、完全可控、且是「无限星球」的唯一可行路径。

**代价（已知并接受）**：失去与 KSP2 截图的血缘关系 —— 程序化能保证「是个有大气/无大气的岩质/气态天体」的**类别身份**，
但保证不了「细看认得出是同一颗星球」。

**目标改为**：**还原原图的「质感」**，即颗粒感、对比度、色感、大气边缘形态对标，而非地图形状对标。

### 4.2 质感是可以量化的（本方案的核心方法）

「质感」被拆解为 **7 个可测数字 + 1 条边缘剖面**，实测值见 §7.2 / §7.3：

| 指标 | 含义 | 用途 |
|---|---|---|
| 亮度均值 μ | 基准曝光 | 生成时对齐 |
| 对比度 σ/μ | 质感浓度 | 噪声振幅 |
| **低频谱斜率 β** | 能量随尺度的衰减 | **质感头号参数**：岩质类 β≈−2.4~−3.5（块面感强），气态/匀质类 β≈−0.3~−1.7（平坦铺开） |
| 高频谱斜率 | 细节锐度 | 实测一律 ≈ −4（见 §8），**说明无需造锐利细节** |
| 颗粒度（3×3 局部标准差中位） | 细节层强度 | 细节层强度标定 |
| 饱和度 + 主色相 | 色板 | 群系配色基准 |
| 边缘亮度剖面 | 大气形态 | **大气散射层的标定参数** |

**验收闭环**：同一套量测代码先测原图（得基准），再测生成图（得结果），数字对得上即达标。
人眼只负责最后确认「好不好看」。

### 4.3 数据形态

```
【源数据】（生产期，可编辑）
  biomeMap.png      群系 ID 图（灰度或索引色，一张一个 ID，不含纹理）
  heightMap.png     高度图（驱动明暗、轮廓位移、法线）
  globalParams      全局参数（色板基准、总体颗粒度、对比度 —— 来自质感量测）

【配置】（仓库，手写/工具生成）
  biomeStyles       每个群系的材质定义 ← 纹理「从哪来」在这里

【生成物】（离线，一次性）
  planet_albedo      基础色图（矩形等距圆柱，2048×1024）
  planet_detail      可平铺细节图（512×512，无缝）
  planet_normal      法线图（由 heightMap 求导）

【运行时】
  网格渲染 → 采样 albedo（低频、大尺度）
           → 叠加 detail（高频、平铺）
           → 光照 + 大气散射 + 云层
```

**关键约定**：`biomeMap` / `heightMap` **只在生产期使用，不进运行时加载清单**。
运行时只加载生成物，`textureManager` 无需改动。

### 4.4 群系如何产生差异（`biomeStyles`）

群系看起来不同，靠的不是「贴图不同」，而是**参数不同**：

```
{
    palette:      ['#c8a86a', '#a8874f', '#8a6a3c'],   // 色板
    heightBias:   0.35,          // 在高度图上的倾向
    heightRange:  [0.2, 0.6],    // 只出现在此高度区间
    noise: {
        type:   'dune',          // dune / fbm / crater / crack / band / continent / coast / vortex
        scale:  18,              // 特征尺度（像素周期）
        octaves: 5,
        warp:   0.4              // domain warp 强度 → 决定「流动感」
    },
    detailBoost:  1.2,           // 细节层强度倍率
    edgeBlend:    24             // 与相邻群系的过渡宽度（像素）
}
```

**`edgeBlend` 是必须项**：群系硬边界会像「贴瓷砖」，需要 8–32px 过渡带才自然。

**噪声算子清单（7 个）与对应天体类型**：

| 算子 | 用于 | 对应天体（β 实测值） |
|---|---|---|
| `crater` | 陨石坑（泊松分布碗形凹陷 + 边缘隆起） | Mun −2.38、Minmus −3.51 |
| `fbm` | 通用基底 | 全部 |
| `continent` | 海陆阈值切分 | Kerbin −3.37 |
| `coast` | 海岸线细化 | Kerbin |
| `band` | 纬向条带 | Jool −1.75 |
| `vortex` | 涡旋 | Jool、Eve −0.79 |
| `crack` | 裂纹 | Moho −0.34、Vall、Eeloo |

### 4.5 群系的可见性限制（影响投入判断）

游戏内天体常见屏幕半径为 **50–400px**。当 Kerbin 半径仅 80px 时，
占表面 10% 的群系在屏幕上不足 8px，**群系差别不可见**。

**结论**：群系化的价值集中在**中近景（≥150px 半径）**；远景观感主要由
**基础色基调 + 大气散射 + 光晕**决定。这三样才是投入重点。

## 五、技术方案

### 5.1 呈现方式与渲染路径

游戏为 **2D 正上方俯视**，但内部走 **3D 网格**：

```
矩形等距圆柱贴图（群系/高度 → 烘焙 albedo + detail）
        ↓ 经纬度 UV
   3D 网格（常规天体 128×64 段；不规则天体 32×16 段 + 低阶径向函数）
        ↓ 正交俯视投影
   2D 画面
```

**为什么统一走网格（D11）**：

1. 不规则天体（Bop / Gilly / Pol / Vall，见 §7.1）**必须**用网格 ——
   其轮廓是「直线段 + 折角」的低模特征，平滑径向位移会把折角磨圆，丢失性格
2. 既然网格管线逃不掉，再维护一条「片元着色器球面求交」路径就是纯负担
3. 统一后，为片元路径设计的各种妥协（极点压缩、边缘 5 倍拉伸、投影转换）**全部消失**
4. 未来的轴向倾角、镜头旋转、无限星球都是同一条路

**代价**：多约 3–5 人日（网格管线），但省掉极视图转换与双路径维护，净成本持平。

### 5.2 自转：俯视视角的固有限制

> ⚠️ **2026-09-26 订正：本节的论证有误，结论需重新表述（原文保留在下方）**
>
> 原文写「若天体自转轴正对镜头……**画面与原图完全一致**（绕视线轴旋转在正射投影下是恒等变换）」
> —— **括号里的数学是错的**。球面点绕视线轴转 α 后，正交投影位置从 `(x, y)` 变为
> `(x·cosα − y·sinα, x·sinα + y·cosα)`，**位置确实改变**，表现为纹理绕盘心旋转；
> 只有当球面完全均匀（没有任何纹理）时画面才不变。
>
> **实测**（纯 Node 几何验证：`mun-albedo.png` 2048×1024 等距圆柱按两种投影采样，
> 比较 spin 0° → 45° 的逐像素差，0~255 灰阶）：
>
> | 环带 | 北极俯视对应纬度 | 平均绝对差 |
> |---|---|---|
> | r 0.0~0.1 | ≈87°N | **4.94** ← 唯一"几乎不变"的区域 |
> | r 0.1~0.2 | ≈81°N | 12.69 |
> | r 0.2~0.3 | ≈76°N | 21.73 |
> | r 0.3~0.5 | ≈63~70°N | 30.12 ~ 31.73 |
> | r 0.5~0.7 | ≈49~57°N | 30.15 ~ 36.36 |
> | r 0.7~0.9 | ≈32~41°N | 44.36 ~ **59.49** ← 最明显 |
> | r 0.9~1.0 | ≈18°N | 48.93 |
> | **全盘** | — | **40.46** |
>
> ⇒ **北极俯视下自转是清晰可见的。** 只有盘心 r<0.1（占盘面 **1%**）因极点在等距圆柱上
> 退化（整圈经度被压到一个点）而几乎不变。原文很可能是把「极点邻域退化」
> 误当成了「整个画面不变」。
>
> **因此 τ 要不要做，依据不是"能不能看见自转"，而是下面两条：**
>
> | τ | 画面表现 |
> |---|---|
> | 0° | 自转**可见**（见上表），但**画面中心恒为极点** |
> | **20–25°（推荐）** | 画面中心移到 65–70°N，**符合真实行星的自转轴倾角**（地球黄赤交角 23.4°），且极地不再永远占据正中 |
>
> 补充依据：τ=0 时玩家永远盯着极点看，而极地群系占球面约 **21%** ——
> 视野内容偏单调，这才是"要不要倾斜"真正的取舍点。
>
> 本订正的实测命令与结论同时记入 `ksp-renderlab/docs/交接文档.md` §13.27。

**（以下为原文，保留存档）**

**若天体自转轴正对镜头，则无论转多少圈，画面与原图完全一致**（绕视线轴旋转在正射投影下是恒等变换）。

因此**自转必须靠轴向倾角 τ 才能被看见**：

| τ | 画面表现 |
|---|---|
| 0° | 完全静止 |
| **20–25°（推荐）** | 安静的转动感，赤道区在边缘进出视野 |

τ 为每颗天体可调参数，需新增到天体配置。

### 5.3 不规则天体

**识别结果见 §7.1**：Bop（7.74%）、Gilly（4.49%）、Pol（3.35%）、Vall（2.98%）为不规则体，
其余 13 个为球（偏差 ≤1.94%，其中 Jool 0.17%、Laythe 0.30% 为完美圆）。

**做法**：

```
径向函数 r(θ,φ) = R₀ · [1 + Σ 低阶谐波项]
· 阶数刻意取低（3–6 阶）→ 保留「球体聚合」的块状感
· 网格分辨率 32×16（约 1024 三角形）→ 轮廓自然出现棱面
· 法线用 flat shading（逐面）→ 得到硬边折角
· 凸体：三角形按深度排序后由远到近绘制（无需深度缓冲）
```

**贴图侧不变**：仍用矩形等距圆柱图，按经纬度做 UV。
**表面细节的锐度由贴图承载** —— 网格仅 1024 面，密集小陨石坑画在贴图上即可（Gilly 原图证明其视觉重量本就在 albedo 上）。

### 5.4 光照模型（特效层与星球系统共用）

⚠️ **这是接口决策，必须一次性设计好，不能事后补**：

- 「飞船被星球遮挡光源」与「天体明暗面随太阳位置变化」必须**共用同一套光照模型**
- 2D 俯视下阴影是**圆柱阴影**：太阳在 2D 平面某方向，天体投出一条带状阴影

**飞船侧成本极低**（实测：飞船贴图纯白，平均 RGB 255,255,255）——
直接在绘制时乘光照系数即可，无需抠烘焙光照。

### 5.5 恒星、星环、光晕

| 对象 | 现状 | 说明 |
|---|---|---|
| 恒星 Kerbol | 贴图盘内从中心 186 亮到边缘 251（近全白），**盘外无任何像素**（实测） | 泛光 / 日冕 / 星芒**全部必须程序生成**；主色实测 `#FEC753`（配置里 `#ffcc44` 不一致，需统一） |
| 星环 | **原图无星环**（Dres 盘外仅 416 个有色像素，紧贴边缘，非环带） | 现有环是 `bodyRenderables.js` 里 Canvas 2D 硬编码的 4 段环带；全量提升需做成**前后分层**（背面部分画在星球之下，正面部分之上） |
| 光晕 | 由 `programEffects.js` 的 `createRadialGradient` 实现 | 需 GPU 重做，并对齐现有 Kerbol LOD 插值行为（见 §6.3） |

### 5.6 图层顺序（⚠️ 不是单一插入点）

现有绘制顺序（`src/renderer.js` 的 `render()`，第 320 行起）：

```
黑底 → 星空 → 天体轨道线 → 【每个天体：贴图/光晕 → SOI 边界圆 → 危险警示环】
     → 飞船 → 设施 → 活动飞船轨道线
```

因此 WebGL 层需要**分阶段插入**：

| 阶段 | 位置 | 内容 |
|---|---|---|
| ① | 天体之前/同时 | 星球本体、光晕、星环背面 |
| ② | 飞船之后 | 粒子、舷窗光、阴影 |
| ③ | 全部之后 | 后处理（泛光/色差/折射） |

**后处理需要采样下方画面**（双 canvas 无法直接采样），阶段 ③ 需要把 WebGL 作为最终合成器。
**不阻塞前两阶段，但架构要在阶段 ① 时预留。**

### 6.2 原型对外接口（迁移时无痛，务必按此设计）

```
createPlanetRenderer(gl)                → 创建实例
renderer.setPlanet(bodyParams)          → 换天体（贴图 / 几何 / 大气参数）
renderer.setCamera({ cx, cy, zoom })    → 俯视正交相机
renderer.render(dt)                     → 画一帧
renderer.resize(w, h, dpr)              → 尺寸变化
```

内部完全不接触 `gameState` / `eventBus` / `sceneManager`；
形状与 `sceneManager.render(ctx)` 契约对齐，接入时即加一行调用。

### 6.3 必须复刻的现有行为

| 行为 | 位置 | 说明 |
|---|---|---|
| Kerbol LOD 分级 | `bodyRenderables.js`（`nearScreenR: 200` / `farScreenR: 100`）+ `renderer.js:357-403` | 过渡区用 `easeInOut` 对贴图 alpha 与**光晕 scale** 双向插值。GPU 重做必须对齐，否则缩放穿越阈值时亮度/尺寸会突跳。**建议提取为共享函数** |
| 星空整层淡出 | `renderer.js` 的 `computeStarfieldVisibility` | 靠近恒星时星空淡出，与 GPU 光晕的能量叠加关系需复核 |
| 星空离屏缓存 | `renderer.js`（0.2.5 B9） | 性能优化，保留 |
| 大圆虚线环降级 | `renderer.js`（`DASHED_RING_MAX_RADIUS`） | 性能保护，保留 |

### 6.4 必须注意的两个坑

**① `structuredClone` 丢字段**
`src/physics/celestialBody.js:64` 注释明确：切换星系时天体经 `structuredClone` 克隆，
**只保留自有属性**。任何新增字段（轴倾角 τ、自转速率、大气参数、云参数）**必须在构造函数里显式透传**，
否则切星系后静默丢失。

**② 追踪站复用同一个 renderer**
`src/scenes/trackingScene.js:489` 调用同一个 `render()`。WebGL 层需**按场景开关**，
否则追踪站地图上也会出现光晕与粒子。

### 6.5 数据来源：粒子系统的发动机数据

`Events.SHIP_THRUST_STARTED` / `SHIP_THRUST_ENDED` 在 `eventBus.js` 中已定义，
但**全项目没有任何地方 emit**（只有 `flightScene.js:1066` 发过一次 `THRUST_ENDED` 的燃料耗尽分支）。
`SHIP_DESTROYED` 可用（`atmosphere.js:97`）。

**建议**：粒子系统每帧**直读**活动飞船的 `throttle` / `heading` / `modules`（与特效层「只读现有单例」的定位一致），
爆炸绑定已有的 `SHIP_DESTROYED`。**不改动物理/场景层。**

### 7.2 质感指标（6 个代表天体）

方法：图心 512×512 窗口 + Hann 窗 + 去均值 + 迭代 radix-2 FFT；

| Eve | 128.6 | 11.5% | 0.53 | **0.560 紫黄** | −0.79 | −3.94 |

**读法**：
- **β 把天体劈成两类**：岩质/类地（Mun −2.38、Minmus −3.51、Kerbin −3.37）能量集中低频、块面感强；

- **对比度跨类差 3 倍**（Mun 22.7% vs Jool 7.8%），是「质感浓度」的直接刻度
- **颗粒度是最直接的验收指标**，可在生成图上直接测

## 八、重要修正记录（被实测推翻的判断）

> 这一节的作用是**防止后续重复走弯路**。以下三条都曾在讨论中被当作前提。

| # | 曾判断 | 实测结论 |
|---|---|---|
| **1** | 「贴图光照已烘焙，亮面方向固定，做动态光照必须把 albedo 与光照解耦」（设想稿 §2.7） | **不成立**。Lambert 模型 `L = amb + diff·max(0, n·s)` 全网格搜索拟合，**7/7 天体方差解释率为负**（−30% ~ −288%），即拟合比常数模型更差。逐像素扫描确认：左右/上下对称位置亮度差普遍在 ±10% 内，**无晨昏线、无单侧阴影**。原图是**接近平光**的，只有一个很弱的径向渐变（且方向因天体而异）。<br>→ **程序化生成后直接叠动态光照即可，无需解耦**；也无需担心烘焙光影与新光影打架 |
| **2** | 「大气可从原图边缘带提取」 | **不成立**。边缘亮带只占半径 **2–4%**（约 25px / 1267px），在游戏实际屏幕尺寸（半径 50–400px）下仅 **1–8px**，会显示成一条生硬亮边，**完全不是大气散射的观感**。<br>→ **大气必须程序生成新层**；但亮带的**剖面形状**可作为散射参数标定 |
| **3** | 「不规则体可用高分辨率球 + 平滑径向位移实现」 | **不成立**。Gilly 原图显示其轮廓是「**直线段 + 折角**」的低模网格特征，而非平滑曲线。平滑位移会把折角磨圆 —— 形状对了，**性格没了**。<br>→ **必须走网格**（见 §5.3） |
| **4** | 曾设计「极视图（pole-on map）」方案以规避等距圆柱的极点压缩 | **已作废**。在 D11「统一走网格」决策后，极点压缩问题由网格 UV 天然解决，不需要极视图 |

### 附带结论：高频谱斜率 ≈ −4 的含义

原图是 **3D 球体渲染后截取的画面**，截图分辨率高于游戏实际渲染纹理分辨率，
放大时的插值把高频抹平了。全部 6 颗天体高频斜率都在 −3.9 ~ −5.0（自然地形通常为 −2 ~ −3）。

**对本方案是正面消息**：
> 程序化生成**不需要**造出很锐的细节 —— 原图本来就没有。
> 要匹配的是一个「放大过的、中等尺度」的质感，fBm 噪声**天然就是这个形状**，
> 无需额外做锐化或细节合成。

## 十、实测数据复现方法
